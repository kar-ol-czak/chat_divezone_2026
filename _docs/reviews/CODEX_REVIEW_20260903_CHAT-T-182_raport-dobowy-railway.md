## Findings

1. **HIGH — “full 24h” and “clean” are asserted without checking log completeness.** The builder accepts any existing file containing at least one matching measurement, then unconditionally says “pelne 24h” and may classify it as clean ([summary:185](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:185), [summary:194](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:194), [summary:203](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:203), [summary:212](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:212)). Malformed or future-format lines are silently discarded ([summary:75](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:75)). A seven-hour log, a log with a multi-hour monitor outage, or a mixed old/new format can therefore produce a misleading clean full-day report.

2. **MEDIUM — Selecting one filename does not strictly enforce the previous Warsaw-day window.** The summary reads only `railway_monitor_<date>.log` and never verifies that each UTC timestamp converts into the requested Warsaw date ([summary:187](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:187)). In the producer, WAW time is captured before all probes, UTC time after them, while the destination filename is chosen only when the line is finally written ([monitor:239](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_monitor.php:239), [monitor:252](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_monitor.php:252), [monitor:259](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_monitor.php:259), [monitor:264](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_monitor.php:264), [monitor:75](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_monitor.php:75)). A cycle crossing midnight can consequently land in D+1 with a WAW timestamp from D, causing an off-by-one count despite the requirement that even one mismatch be reported.

3. **MEDIUM — deduplication is neither atomic nor checked for successful persistence.** The code performs `file_exists()`, sends mail, then suppresses errors from `file_put_contents()` without checking its return value ([summary:291](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:291), [summary:303](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:303)). Concurrent executions can both pass the check and send. A permissions/disk failure can also return `sent` without creating the flag, allowing the cron path to resend later.

4. **MEDIUM — failure windows treat periods with no measurements as proven downtime.** The parser computes inter-sample gaps but uses them only for the median ([summary:92](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:92), [summary:125](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:125)). A window remains open until the next parsed `pg_select1 OK`, regardless of elapsed time or an intervening `# START` restart ([summary:108](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:108)). Thus a FAIL before a monitor gap and a FAIL after it become one continuous outage whose duration includes an unobserved interval.

5. **MEDIUM — displayed window endpoints and computed durations use timestamps captured at different moments.** Labels come from the WAW field, while duration uses the UTC field ([summary:78](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:78), [summary:109](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:109)). The monitor captures WAW before TCP/PG/GitHub probes and UTC only after them ([monitor:239](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_monitor.php:239), [monitor:252](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_monitor.php:252), [monitor:259](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_monitor.php:259)). During slow failures these can differ materially, so the printed endpoint subtraction may not agree with the reported duration. The chosen definition of “sample timestamp” needs to be explicit.

6. **LOW — `### ALERT` count is mislabeled as successfully sent alert mail.** Every alert line is counted indiscriminately ([summary:75](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:75)), although the producer writes both `mail=sent` and `mail=FAILED` variants ([monitor:289](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_monitor.php:289)). The report then calls the value “Maile alertowe” ([summary:267](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:267)). It is actually alert attempts/records, not necessarily delivered mail.

7. **LOW — Warsaw DST days are represented incorrectly or ambiguously.** The report always states “pelne 24h,” although a Warsaw calendar day can be shorter or longer ([summary:203](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:203)). Windows retain only `HH:MM:SS`, without offset, and are later sorted lexicographically ([summary:109](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:109), [summary:252](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:252)). During the repeated autumn hour, two different instants can therefore have indistinguishable labels and misleading ordering. UTC duration calculation itself avoids a negative duration.

8. **LOW — incident parsing has silent environmental assumptions.** It requires exact numeric-IP GNU/Linux headers and an English, dot-decimal `packet loss` line, while both target IPs are duplicated as literals ([summary:145](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:145), [summary:160](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:160)). The monitor currently emits compatible commands with those IPs ([monitor:123](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_monitor.php:123)), so current production data works. If `ping` is killed before its summary, localized, or the endpoint changes, the report silently shows `n/d`; it does not distinguish incomplete capture from an unsupported format.

9. **LOW / TEST GAP — dry-run is side-effect-safe but not an end-to-end test of the required contract.** It bypasses `railway_summary_send()`, supplies the date directly, and therefore exercises neither previous-day calculation, dedup statuses nor flag creation failure ([summary:317](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:317), [summary:285](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:285)). Its displayed subject also omits the actual cron subject’s `(fallback)` suffix ([summary:301](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:301), [summary:328](/Users/karol/Documents/3_DIVEZONE/Aplikacje/Chat_dla_klientow_2026/_docs/scripts/railway_summary_mail.php:328)).
